# 変更の進め方

変更の範囲、Git / PR の運用、検証とレビューの手順を扱います。構造のルールは
[AGENTS.md](../AGENTS.md)、設計の判断原則は [ARCHITECTURE.md](ARCHITECTURE.md)、
内部契約は [specs/](specs/README.md) を正本とします。

## 作業範囲

- 依頼範囲外の変更や、未コミットの差分に手を触れない。
- シークレット、資格情報、実環境固有の値をコードやリポジトリに含めない。
- コメント・ドキュメント・説明は日本語で簡潔に書く。識別子・API・技術用語は無理に日本語化しない。
- 不要な抽象化・空モジュール・重複実装を作らない（YAGNI）。

## ブランチと PR

- `git fetch origin develop` で最新化し、`origin/develop` から作業ブランチを分岐する。
- Stacked PR は依存元ブランチから分岐し、PR 作成時も `--base <依存元ブランチ>` を指定する。
- ブランチ名は `<type>/<概要>` または `<type>/<issue番号>-<概要>`。`type` は `feat`、`fix`、`refactor`、`docs`、`chore` など。
- 指示を受けて新規作成する PR は、差分確認のため原則 Draft とし、テンプレート・ラベル・`@me` アサインを揃える。
- 実装・検証が完了したら Open（Ready for review）にし、以降の追加修正やレビュー対応で勝手に Draft へ戻さない。
- 参照はフル URL ではなく `PR #<番号>`、`Issue #<番号>`、7 桁 SHA で書く。外部リポジトリは `owner/repo#<番号>` を使う。

## 検証

- 変更関連のテストと CI を必ず通す。テスト条件の緩和で通さない。
- 不具合修正には回帰テストを追加する。
- UI 変更は可能なら実画面で確認する。未確認箇所は再現手順と残存リスクを報告する。
- CI と同じ route をローカルで実行する。手順は `.opencode/skills/run-ci/SKILL.md` を正本とする。例外を増やして回避しない。
- レビューでは不具合、データ損失、セキュリティ、並行性、リーク、テスト不足を最優先する。

## レビュー指摘への対応

- 指摘を反射的にオウム返しせず、場当たり的な局所パッチ（ワークアラウンド）を追加しない。
- 指摘が「局所的な実装漏れ」か「設計・状態の所有境界の歪み」かを判断する。根本的な見直しが必要なら、コードを継ぎ接ぎせず人間に相談する。
- 修正コミット後は、PR または該当スレッドに次を明記して返信する。
  - **対応内容**: 変更箇所の概要
  - **判断・理由**: その修正にした理由
  - **コミット**: 7 桁 SHA

## ドキュメント

- 実行時の挙動はコードとテストを正本とし、内部契約・設計制約は `docs/specs/` を正本とする。未確定事項や推測を恒久仕様化しない。
- ドキュメントの一括読み込みは禁止。作業対象の領域の `README.md` と必要な仕様書だけを読む。
- 全体の分類は [docs/README.md](README.md) に従う。コードやテストで十分なら新規文書を作らず、新設時は「誰が何を判断するために必要か」を書く。
- 仕様変更時は、正本となる関連文書を更新し、不要になった記述を削除する。
